name: helm-commons
description: Set up a Helm chart that deploys an upstream chart using the domain-specific common chart. Use when the user wants to package or deploy an upstream Helm chart in a repo scaffolded with skaffold and the private common chart.
---

## Workflow

1. Ensure that the correct template has been generated by the user. Check for a `skaffold.yaml`,
   and a `helm/Chart.yaml` that includes the common chart from the local private repository. Note
   a Bitnami common chart does not meet this requirement. The Bitnami common chart _may_ be
   included but the domain specific chart must _also_ be included. For basic patterns, read
   [references/skaffold.yaml](references/skaffold.yaml) and
   [references/Dockerfile](references/Dockerfile), found next to this file in the skill's
   directory.
2. The user will provide the helm chart they desire, if they provide the specific chart and
   registry, use that, otherwise, research the chart and give the user options to pick from.
3. Add the chart as a subchart dependency and ask the user to run the `helm dep update helm`,
   or the appropriate command to download the charts.
4. Understand both the common chart and the upstream, and set up the values based on the user's
   specifications. Ensure common behavior is used unless additional templates are absolutely
   necessary. Check the existing Kubernetes cluster with the `kubernetes` MCP server's tools to
   determine anything not specified in the common chart default values. The general
   requirements are:

   - When available/appropriate, setup OIDC SSO with the authentik, ask the user for the
     necessary details _except_ secret. Use the common chart to write out values with
     obvious bogus values that the user can replace for secrets.
   - Ensure backup cron jobs exist when the upstream includes support. Important: When it looks
     like backups would be useful but either the upstream chart does not include support, or
     the upstream chart uses Bitnami charts for the backup, prompt the user what to do.
   - Use "capacity" style storage classes for any storage that is large or doesn't need low
     latency (user uploaded content, large media, etc.). Use "performance" style storage
     classes rarely, only for latency sensitive storage like databases.
   - Use RWO block storage whenever possible.
   - Only use RWM file storage when accessing content already on NAS-style storage or when
     absolutely necessary.
   - Containers must run securely, ensure they comply with the "restricted" Pod Security Admission
     policy. This may require building a custom container image to run as non-root. If so, try to
     use the normal upstream as the base and make only minimal changes. The container should
     use a FROM line that uses an env variable that then gets filled in by skaffold.
5. Setup an appropriate Renovate.json only if necessary. Version patterns in the referenced
   examples assume a base renovate configuration that supports them.
